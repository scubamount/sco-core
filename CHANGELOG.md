# Changelog

What each change means for plugin authors and for products built on sco-core (sc-offline). SDK releases are tagged `sdk-v<version>` and published with `sco-sdk-<version>.zip`; between releases, sc-offline pins a commit.

## Unreleased

- **Game pack: the mission script library lookup** (`sco_api.h` unchanged; for sc-offline #85, whose no-scans gate has no allow-list; [game services](docs/game-services.md#internal-game-pack-helpers)). **`sco/game/missions.h`** adds `sco::game::missions::ScriptLibrary(manager, &reason)` (`src/game/services/missions.cpp`, library `sco_game_services`, Windows): the derivation sc-offline's `missions.cpp` did with a raw `BytesMatch` on a function reached through the live mission manager, moved here byte for byte. It reads `vtable(manager)[0x48]`, checks `48 8B 4B` at `+0x32` of that function, and returns `*(manager + function[0x35])`, all under `__try` (a fault now answers 0, where it used to crash). Not a service and not an ABI: no table, nothing in the SDK zip. Failure gives one of two stable strings, `kReasonNotFound` ("the mission manager's script library wasn't found") and `kReasonNotYet` ("the script library isn't there yet"), so sc-offline logs the same lines as before. The constants (slot `0x48`, canary offset `0x32`, displacement byte `0x35`) are documented as checked at runtime, never trusted; the function is not the `missions.load_all` row (that one's bytes at `+0x32` are `39 63 08 48`), which is why it can't be a row. No new rows; the game pack's version line is unchanged. Tests: none new, the lookup needs a live mission manager (a running game); `sco-sigcheck` still resolves every row. For sc-offline: call it instead of the inline reads and drop `BytesMatch` from `missions.cpp`.

- **Game services, and the game pack's own version line** (`sco_api.h` unchanged; [design](docs/design/game-services.md) PR 2, part 1; [game services](docs/game-services.md)). `sco::host::ProvideGameService` / `WithdrawGameService(s)` / `GameOwner` (`sco/host.h`) publish under the reserved owner `game`: names `game.<name>`, plus the product names a game pack took over (`kGameCompatNames`: `teleport.spatial`, `spawn.entities`). **`teleport.spatial` 1.0 moves into the game pack** (`src/game/services/`, library `sco_game_services`, Windows): the same table and version, with the zone-tree code moved from sc-offline's `teleport` built-in and the player/zone reads from its `teleport.cpp` and `build.cpp`, same offsets. A product turns the game services on with `sco::app::Platform::gameServices` (off by default, so a product that still publishes the name keeps working); `Start` publishes them before any plugin loads and `Stop` withdraws them after `UnloadAll`. **`sc_game_pack.h`**: `SCO_GAME_PACK_VERSION` `0.1.0` and the newest verified game build; [`docs/game-pack.md`](docs/game-pack.md) lists every verified build (4.10.196.36804: all rows OK in `sco-sigcheck`). The SDK zip ships both, plus `docs/game-services.md`, and `sdk/package.py` prints the kernel and game-pack versions. Tests: `test_host` TestGameServices; `test_app` publishes and withdraws `teleport.spatial` with `gameServices` (Windows builds).

- **sc-offline's feature scans are now sco-core signature rows** (`sco_api.h` unchanged; five groups, one table each). Five new tables under `include/sco/game/` with their rows in `src/game/`: `world_sigs.cpp` (36 rows: build mode, free cam, the ray and camera addresses, missions, cvar storage, quantum boost), `contracts_sigs.cpp` (83 rows and 15 capabilities behind sc-offline's contracts feature), `offline_sigs.cpp` (60 rows and 19 capabilities behind the offline patches, boot and startup hooks), `features_sigs.cpp` (the rows behind sc-offline's five `FindPattern` scans: fly mode, Clear NPCs, effect tag, reputation checks and the OR-loop bound) and `actors_sigs.cpp` (33 rows: spawning, Clear NPCs' direct removal, ammo and the player loadout). `RegisterGameSignatures` registers all of them; every row carries its capability and `tests/test_core.cpp` now checks each table's rows are all covered by a capability. The integrated tables resolve **300/300 rows OK** against Star Citizen 4.10.196.36804 (report saved with the build's baseline); each group was checked against the same build before it was merged. Doc pages: [world](docs/game/world.md), [contracts](docs/game/contracts.md), [offline](docs/game/offline.md), [features](docs/game/features.md), [actors](docs/game/actors.md). Nothing changed in the game: the addresses resolve to the same ones sc-offline's scans found, and sc-offline still uses its own scans until it repins and drops them (its own PRs).

- **The kernel builds and tests without the Star Citizen game pack** (`sco_api.h` unchanged; maintainer's Step 2.5 of 2026-10-10; [architecture](docs/architecture.md#kernel-and-game-pack)). A new CMake option `SCO_GAME_SC` (`ON` by default) builds the game pack: the `src/game` rows move out of `sco_core` into a new library **`sco_game_sc`** (which `sco_pak`, `sco_app` and `sco-sigcheck` link, so a product that links them, sc-offline included, gets the rows exactly as before), and `sco_pak`, `sco_datacore`, `sco_datacore_service`, `sco-sigcheck` and `sco-dcb` are built only with it. With `OFF`, `SCO_KERNEL_ONLY` is defined: `sco::app::Start` logs `sco.datacore not started: this build has no game pack` for `Platform::dataCore`, `sco-host-sim` skips the pack lint and the game tables, and the game-row and DataCore tests are left out. CI's new `kernel-only` job (`cmake.yml`) builds that way with ASan and UBSan, fails if a game-pack object or symbol was built, and runs the tests.

- **Hardening: sco-lua, the host table and the release workflow** (`sco_api.h` unchanged; from the 2026-10-10 audit). **sco-lua:** `sco.run_on_game_thread` takes its registry reference before it allocates the task, so running out of memory there no longer leaks the task (H1); and a new cap, `SCO_LUA_TOTAL_MEMORY_LIMIT` (256 MiB, `plugins/lua/sco_lua.h`), limits the memory of every script together on top of the 64 MiB per script, so many scripts can't exhaust the game's memory between them; past it an allocation fails with `not enough memory` in whichever script asked, exactly as at the per-script cap (M2; `tests/test_lua.cpp` TestTotalMemory); and `sco.invoke`, like every other call, now answers `unavailable` from a script that was disabled while an outer call of it is still running (L2). **Host:** `log` and `status` turn CR and LF in a plugin's text into spaces, so a plugin can't write lines of its own into `mod.log`, such as a fake `[core]` line (L4; `tests/test_host.cpp`). **Release workflow:** packaging and checking the SDK run with read-only repository access in a job of their own; only the job that creates the release, which runs no build step, can write (L6). Not changed, by decision: the per-call step accounting (H2, to be measured first), the 512 command slots (L5) and services' direct tables (M1).
- **The host kit no longer registers Star Citizen's signature tables by itself** (`sco_api.h` unchanged; maintainer's Step 2 of 2026-10-10). `sco::app::Platform` gains `registerSignatures` (`bool (*)()`, default null): with `image` set, `sco::app::Start` calls it before `ResolveAll`, where it used to call `sco::game::RegisterGameSignatures()` unconditionally. A host for another game (or `sco-host-sim` without `--exe`) no longer scans for Star Citizen's rows. Products that pass an image set `pf.registerSignatures = sco::game::RegisterGameSignatures`; `sco-host-sim` does. sc-offline is unaffected: it registers and resolves the game tables itself in `StartOffline`, before its patches, and starts the host kit without an image.

- **`sco.net` 1.0, the host service, plan PR 4b** (design [section 3.1](docs/design/multiplayer.md#31-sconet-10-a-session-and-typed-channels-game-agnostic) and its as-built note; `sco_api.h` unchanged; [plugin guide](docs/net.md)). **`include/sco_net.h`**, a host-owned service pinned by `tests/abi_net.c` (64 bytes): `is_active`, `get_peers` (self first; the size handshake), `get_peer_name` (a sized copy, never cut inside a UTF-8 character), `send_channel`, `register_channel` (flags `SCO_NET_RELIABLE` / `FROM_HOST` / `TO_HOST`, a `max_len`, a callback and ctx), `unregister_channel`, `self_peer`; `sco_result` returns; events `net.state` and `net.peer` (JOINED, LEFT, ENTITY). A plugin registers and sends only on `<its id>.<name>`; per-plugin send quotas of 256 messages and 512 KiB per second (`SCO_TOO_MANY`); its channels and queued messages go when it unloads or crashes. The host sets the capability `sco.net`, so `requires = sco.net` validates. **Threads:** one network thread per session owns `sco::net::Core` and the socket and never calls plugin code; plugin calls are copied and queued to it; messages and events reach plugins only from `sco::net::Tick` on the game thread, as guarded callouts. **Session control is the product's only** (`include/sco/net/session.h`: `Host`, `Join`, `Leave`, state, `SetPeerEntity`), not in the plugin table; nothing opens a socket until the product calls `Host` or `Join`. **UDP:** `src/net/udp_win.cpp` (Winsock; CONTRIBUTING's Windows-headers list grows by it) and `udp_posix.cpp`. **LAN only by default** (`sco/net/scope.h`): loopback, RFC 1918 and link-local; extra CIDRs (Tailscale's `100.64.0.0/10`, a ZeroTier range) only through the product's allow-list; everything else is dropped before parsing and `Join` refuses it. Library `sco_net_service`; the host kit starts it, delivers from `Tick` and stops it after `UnloadAll`. **`scosdk/net.hpp`** (`Net`, `NetChannel` with lambdas). The SDK zip ships `sco_net.h` and `docs/net.md`. Tests: `tests/test_net_service.cpp` under ASan+UBSan and TSan (and CTest, on Windows too): ownership and name refusals, quotas over a virtual clock, directions, delivery only on the game thread, release on unload, hosting and joining over the in-memory network (wrong passphrase included), the LAN rule, two Cores over UDP loopback, and the service's network thread over UDP loopback with table calls from 8 threads; `test_app` checks a plugin with `requires = sco.net` loads. Follow-ups: the C# and Lua layers, a two-process `sco-host-sim` test with a `net_echo` example, IPv6 sockets, and dropping a peer that floods. For sc-offline: link `sco_net_service` (the host kit does); its `builtins/multiplayer` calls `sco::net::Host` / `Join` (plan PR 7).
- **The bridge layouts move into the SDK, MIT** (maintainer's decisions of 2026-10-10: the TitanLink Northstar side becomes its own plugin built against the SDK, and the bridge layout headers are MIT; `sco_api.h` unchanged; [docs](docs/ipc.md#bridge-layouts)). **`include/sc_titanlink.h`** (`Local\SCO_titanlink.link`, `TL_LAYOUT_VERSION` 1) and **`include/sc_voxel_bridge.h`** (`Local\SCO_voxel_bridge.link`, `VX_LAYOUT_VERSION` 1): the channel layouts sc-offline's `titanlink` and `voxel_bridge` built-ins used as `titanlink_wire.h` and `voxel_wire.h`, byte for byte (same names, offsets, sizes and constants; no wire change), now header-only C11 / C++20 with freestanding headers only and `SPDX-License-Identifier: MIT`. The interface exception of `LICENSE` and `CONTRIBUTING.md` names them beside `sc_ipc.h` and `sc_net.h`. Both sides of a bridge vendor the header from the SDK, and its `*_LAYOUT_VERSION` must match (`sc_ipc_attach` refuses another). Every struct size and field offset is `static_assert`ed in the headers; `tests/abi_titanlink.c` and `tests/abi_voxel_bridge.c` pin every size, offset and constant (the five ways, and each header on its own as C11 and C++20; CTest `abi_titanlink`, `abi_voxel_bridge`). The SDK zip ships both. For sc-offline: include them from `external/sco-core/include` and delete its local copies.
- **`sco.net` core, plan PR 4a** (design [section 3.5](docs/design/multiplayer.md#35-session-crypto-d4); `sco_api.h` unchanged; [wire format](docs/net-wire.md)): the platform-free half of `sco.net`, library `sco_net` (`src/net/`, internal headers `include/sco/net/`). **`include/sc_net.h`, MIT** (maintainer's roadmap ADR-003; the interface exception of `LICENSE` and `CONTRIBUTING.md` now names it beside `sc_ipc.h`): the wire as a header-only C11 / C++20 file with freestanding headers only, for programs outside sco-core: constants and limits, kinds, header offsets, body layouts, codes, `sc_net_parse`, `sc_net_write_header`, the MAC input `sc_net_mac_head` and `sc_net_tag` over an HMAC the program supplies, `sc_net_tag_equal`, the replay window, name rules. sco-core's wire code is built on it (one definition), `tests/abi_sc_net.c` pins it (the five ways, and on its own as C11 and C++20; CTest `abi_sc_net`), and the SDK zip ships it with `docs/net-wire.md`. **Crypto:** SHA-256, HMAC-SHA-256 and PBKDF2-HMAC-SHA256 in plain C (`sha2.c`, no OpenSSL), a constant-time compare, `kPbkdf2Iters` = 200,000. **Handshake:** HELLO / CHALLENGE (the host's per-session salt) / PROOF / WELCOME / REFUSE; a wrong passphrase fails the PROOF check and is refused; WELCOME is MACed so a host without the passphrase admits no one; per-link keys from both nonces. **Wire:** a 28-byte header (version, kind, channel index, sender, seq, 32-bit body length), 1,400-byte datagrams, a 16-byte truncated HMAC over the version, the channel's full name, sender, seq and body; a parser that refuses short, truncated, trailing, oversize, bad-magic, bad-version and bad-kind input before reading through any length. **Replay:** monotonic per-link seq, a 1,024-packet sliding window. **Delivery:** unreliable (1,200 bytes) and reliable (256 KiB, 1,200-byte units, 64-unit window, acks with a selective mask, doubling resend, exactly once and in order) over an abstract datagram `Transport`; `sco::net::Core` runs the session as a star (the host relays), with the channel table, FROM_HOST / TO_HOST, the receiver's own `max_len`, keepalive, 30 s timeouts and BYE, all driven by `Pump(nowMs)`. Tests: `tests/test_net.cpp` under ASan+UBSan and TSan (and CTest): the published vectors, every truncation and bit flip of a packet, a seeded fuzz, the replay window against a model, stream edge cases, handshakes (right and wrong passphrase, full, not admitted, version mismatch, a forged WELCOME, no host), tampered, truncated, replayed, spoofed and oversize datagrams, a HELLO flood, reliable delivery of messages up to 256 KiB over a seeded network with 20% loss, 10% duplicates and reordering for four seeds, and four peers in one process (relay, directions, late channels, leave, timeout, rejoin); `tests/net_mem.h` is the in-memory network, on a virtual clock with no sleeps. The decision of 2026-10-10 (`sco.net` lives in sco-core, sockets included) is recorded in the design. Next, plan PR 4b: the UDP sockets, the `sco_net_v1` table, channel ownership, quotas and the capability. For sc-offline: nothing yet.

This adds 62 rows in `src/game/asop_sigs.cpp`, `atc_sigs.cpp` and `hangar_sigs.cpp`, built from Appendix B of the research document on offline ship terminals, lifts, hangars and ATC (4.10.196.36804). Additions that the document doesn't guard: kiosk `+0xA28`, `+0x9F8` and `+0x9E8`, and the landing area's `+0x318` through the new row `landing.unstow_success`. `include/sco/game/asop.h` adds `asop::Capabilities()`, 11 capabilities with their row lists and root causes (for `caps::SetFromSignatures`), and the pinned offsets as constants. `src/game/sig_rows.h` adds table-driven resolvers. `sco-sigcheck` on 4.10.196.36804: 70/70 OK, and every RVA equals the document's. Tests: `TestAsopRows` in `tests/test_core.cpp` covers a fake `OnRequestOpen` with each failure reason and an ambiguous gate site, and checks that every row is in a capability. For sc-offline: add the three `.cpp` files to `src/sc-offline-dll.vcxproj` and read the module's addresses through these rows.
- **SDK: `sc_spawn.h`, sc-offline's `spawn.entities` 1.2** (`sco_api.h` unchanged). `include/sc_spawn.h` is the table sc-offline's `spawn` built-in publishes (until now `src/builtins/spawn_service.h` there), pinned by `tests/abi_spawn.c` (`tools/test.sh`: C11, C++20, `-fshort-enums`, x86_64-pc-windows-msvc) and documented in [API v1 § Built-in services](docs/api-v1.md#built-in-services); it includes `sco_api.h` for `sco_plugin`, as `sco_ipc.h` does. - **`sco.ipc` 1.0 and the MIT wire `sc_ipc.h`** (design [section 3.3](docs/design/multiplayer.md#33-sc_ipch-the-wire-mit-and-the-scoipc-service-the-in-game-wrapper); `sco_api.h` unchanged; [docs](docs/ipc.md)). **`include/sc_ipc.h`**: header-only C11 / C++20 with freestanding headers only, `SPDX-License-Identifier: MIT` (the interface exception, now in `LICENSE` and `CONTRIBUTING.md`), so the non-GPL side of a bridge includes it alone. It defines the 64-byte channel header (magic, version, pids, epoch, both heartbeats, size, layout id/version, state), single-producer single-consumer byte rings (64-bit counters on their own cache lines, power-of-two capacity, the pad record when a record doesn't fit before the end) and seqlock blocks, every layout `static_assert`ed, an atomics shim over compiler builtins (MSVC x64: volatile and compiler barriers), and hostile-peer checks: geometry is validated once against the OS's view size and cached locally, and every counter, length and record header read afterwards is checked before use (`SC_IPC_CORRUPT`, never an access outside the mapping). **`include/sco_ipc.h`**, a host-owned service pinned by `tests/abi_ipc.c`: `create` (`Local\SCO_<plugin id>.<name>`, built by the host; DACL and owner for the current user only; 256 MiB per channel, 512 MiB and 16 channels per plugin), `peer_age_ms`, `block_write` / `block_read`, `ring_init` / `ring_push` / `ring_pop` (one direction per ring, the size handshake), `view`, `close`; ids, never pointers (`view` excepted: the plugin's own mapping). Closed (`SC_IPC_GONE` for the peer), heartbeat stopped and unmapped when the plugin unloads or crashes. Host side `sco/ipc.h`, library `sco_ipc` (`src/ipc/ipc.cpp`, `shm_win.cpp`, and `shm_posix.cpp` for the tests); the host kit starts it, writes the owner heartbeat from `Tick` and stops it after `UnloadAll`. **`scosdk/ipc.hpp`** (`Ipc`, `IpcChannel`). The SDK zip ships both headers and `docs/ipc.md`. Tests: `tests/test_ipc.cpp` under ASan+UBSan and TSan (ring wrap and padding, full/empty, the size handshake, sequence rollover across 2^64, epoch changes, torn headers and blocks, bad magic/version/layout, oversized and impossible lengths, counters and offsets, a seeded fuzz of scribbles, writer/reader threads; the service over real shared memory with the peer as a second mapping opened by name: names, quotas, directions, overlap, a hostile peer, heartbeats, close and unload). Deferred to a follow-up: the C# wrapper and a two-process test. Lua gets no `sco.ipc` (by design). For sc-offline: link `sco_ipc` (the host kit does); nothing else until a bridge uses it.

## sdk-v1.1.0 (2026-10-09)

The first SDK release. The plugin ABI is version 1.1 and stable from here on: version 1 only grows at the end of structs, so plugins built with this SDK keep loading in later 1.x hosts.

- **One ABI, five ways to write a plugin:** C against `sco_api.h`, C++20 with `scosdk/`, C# with `Sco.Sdk` (published with NativeAOT, no .NET needed by players), sandboxed Lua 5.4, and data packs with no code.
- **Host services**, each with its own pinned header: `sco.storage` (per-plugin key-value and SQL over SQLite, crash-safe), `sco.ui` (menu tabs, overlays, badges, hotkeys bound to commands), `sco.datacore` 1.1 (DataCore overrides, new instances and new records, applied at the game's data load or saved for the next launch). Plugins provide services and raw handlers to each other.
- **Data mods that survive game patches:** `.toml` packs address DataCore records and fields by name; `sco-dcb` lints them and checks them against a game build.
- **Host side for products:** the host kit, built-in plugins, crash containment, the detour engine, 64-bit engine math and the zone tree, virtual game files (`sco::vfs`, `sco::game::pak`), and the signature tables with `sco-sigcheck`.
- **SDK zip** `sco-sdk-1.1.0.zip`: headers, template, seven examples (`hello`, `cpp_hello`, `cs_hello`, `greeter`, `notebook`, `travel_pack`, `quantum_pack`), the CMake helper and `sco-plugin-check`, each example built and checked from the zip on Linux and Windows in CI.

Every change since the first commit, newest first:

- **`teleport.to_camera` survives Star Citizen 4.10.196** (the 2026-10-09 patch, `StarCitizen.exe` 4.10.196.36804): the row failed with "layout changed at +0x17a" because the four camera fields the handler loads at +0x17A..+0x1BD moved by 8 bytes (`0x6D3C` -> `0x6D44`, ...); the code around them was unchanged. Those checks now pin the instructions (`vmovss`/`vmovups`/`vmovsd` from `[rax+disp32]`) and wildcard the field offset, which nothing reads. `sco-sigcheck`: 8/8 OK on both 4.10.193.11644 and 4.10.196.36804 (the three dependent `teleport.*` rows resolve again).
- **C# SDK layer** (`sdk/csharp/Sco.Sdk`, [docs](docs/sdk-csharp.md); `sco_api.h` unchanged): a .NET 8 library with no package references over `sco_api.h` 1.1, `sco_storage.h`, `sco_ui.h` and `sco_datacore.h`: blittable `[StructLayout(Sequential)]` structs with `delegate* unmanaged[Cdecl]` function pointers, and wrappers mirroring `scosdk/`: `Plugin` with `OnLoad` / `OnUnload`, logging, `CommandBuilder` / `Args` / `Reply`, `Subscribe` handles (one host subscription per event, handlers multiplexed), `RunOnGameThread`, `Invoke` / `InvokeAsync`, `Provide` / `Query` / `ServiceRef<T>.Covers` with the size check, `RegisterRaw` / `InvokeRaw` with the size handshake, `Storage`, `DataCore` / `DataCorePatch` and `Ui`. Callbacks are `[UnmanagedCallersOnly]` trampolines whose ctx is an id into a registry swept at unload (never a `GCHandle`); command strings live in a native arena until unload; no exception crosses into native code (logged; `SCO_FAILED` and `<name> failed: <message>` for commands). Plugins are published with NativeAOT (`PublishAot`, `NativeLib=Shared`) into one self-contained DLL with the three exports. New example `sdk/examples/cs_hello` (`cs_hello.wave <name>`, `cs_hello.ticks`, the `cs_hello.greeter` service, `game.ready` and `tick`). - **`sco/hook.h` v2**: `StolenLength` (instruction-length decoding for the usual prologue set; refuses RIP-relative and relative-branch code) and `InstallDetour(target, 0, ...)` to count stolen bytes automatically; a far path (`FF 25` absolute jump over 14+ stolen bytes) when no cave fits within ±2 GiB; `MemoryProtectScope` (RAII protection, now under `WriteCode`); `RemoveAll`; opt-in `Transaction` for hooks that only make sense together (sc-offline's independent hooks keep using `InstallDetour`). Existing calls behave as before, except `stolen = 0`, which was `BadArg` and now means "count it". [api.md](docs/api.md#scohookh-detours-and-near-code-memory).
- **`sco/engine/types.h` and `sco/engine/zone.h`** (library `sco_engine`; `sco_api.h` unchanged): header-only 64-bit `Vector3d` / `Quatd` / `Transform`, with `FromXYZW` / `ToXYZW` for the game's (x, y, z, w) `double rot[4]`, and `ZoneTree`, nested zones the host feeds each tick (`Set` / `Remove`) with `LocalToWorld`, `WorldToLocal` and `Transform` between zones (via the common ancestor; false for a missing zone, a cycle or more than 32 levels). Pure math: no game offsets, no game memory; sc-offline keeps reading the game's zones and feeds them in. Groundwork for the spatial service ([framework plan](docs/framework.md)). `tests/test_spatial.cpp` runs under ASan+UBSan and ThreadSanitizer.
- **C++20 SDK layer** (`include/scosdk/`, [docs](docs/sdk-cpp.md)): header-only, over `sco_api.h` 1.1 (unchanged), standard library only. `sco::sdk::Plugin` with `OnLoad`/`OnUnload`, printf-style logging, `RunOnGameThread` and `Subscribe` handles; `SCO_PLUGIN` writes the three exports; `CommandBuilder` with typed `Args`/`Reply`; `Provide`/`ServiceRef<T>`/`HasMember`; `RegisterRaw<In, Out>`/`InvokeRaw` with the size handshake, plus byte-span forms. Every callback's ctx is an id into a registry swept at unload, so nothing the SDK frees can be called late; no exception crosses the C ABI (`SCO_FAILED` and a log line instead). New test `test_sdk` (two SDK plugins through the real host table; ASan+UBSan and TSan in `tools/test.sh`, CTest on Linux and MSVC). The SDK zip ships `include/scosdk/`, `docs/sdk-cpp.md` and the `cpp_hello` example, which `sdk/test-zip.sh` builds and checks with MSVC and gcc. sc-offline needs no change.
- **sco_api 1.1** (`SCO_API_MINOR` 1; 1.0 plugins load unchanged): `SCO_FAILED` (7), the result for a command or service that ran but couldn't do its job (#12). Services: `provide_service(self, name, version, vtable)`, `query_service(name, min_version, out_vtable)`, `release_service(self, name)`, function tables one plugin publishes for others under `<id>.<name>` with `(major << 16) | minor` versions, withdrawn when the provider unloads or crashes ([API v1 § Services](docs/api-v1.md#services-11)). Raw handlers: `register_raw` / `invoke_raw`, byte-in byte-out calls on the game thread with a capability check, the crash guard and a size handshake ([API v1 § Raw handlers](docs/api-v1.md#raw-handlers-11)). `sco_api` grows from 88 to 128 bytes; `tests/abi_v1.c` pins it. The 1.1 service signatures changed before any tag: the `sco_service_def` struct of #14 is gone. Plugins built with this header report api 1.1 in `sco_plugin_info` and need a 1.1 host.
- **Discovery refuses a plugin folder whose id belongs to a built-in** (`the id belongs to a built-in plugin`), for every kind, data packs included (#11). `sco::plugins::Options` gains `builtins` / `nBuiltins`; `sco::app::Start` fills them from `Platform`.
- **`sco/hook.h`** (library `sco_hook`): near-code caves, `WriteCode`, `InstallDetour` / `RemoveDetour` with one detour per target, so a product's hooks and plugins share one patcher. sc-offline's `hooks.cpp` moves onto it next. `tests/test_hook.cpp` detours real code in executable memory on Linux and Windows.
- **Docs: Phases 1-3 done, lessons learned** ([framework plan](docs/framework.md#lessons)): sc-offline builds with CMake (sc-offline PR #55, `88e7830`) and runs on sco-core's host kit (sc-offline PR #56, `78756af`, played in game 2026-10-09; plugins off by default). Five lessons with their rules: call `sco::app::Stop` from the game's quit path, since the game's Quit never sends `WM_QUIT` (`game.exit` is best effort); start the host kit regardless of any one feature; aliases can't share a name with a function; the CMake settings a consumer needs ([building](docs/building.md#using-sco-core-from-another-cmake-project)); plugin loading never shows the Bad Image box (`933701a`, `SetThreadErrorMode`). CONTRIBUTING: lessons flow back to sco-core in the same cycle. README, the SDK status and the docs index describe sc-offline on sco-core. Docs and comments only.
- **`system.quit`** (`sco/game/system.h`, `src/game/system_sigs.cpp`): CSystem::Quit, found from its `CSystem::Quit invoked with - cause=$$, ...` log line, and `sco::game::QuitFunction` (entry plus the 15 whole prologue bytes a detour may overwrite). - **Framework plan** ([docs/framework.md](docs/framework.md)): proposal for sco-core as the heart of a framework for mods of any kind: a host kit products start from, built-in plugins, local storage (key-value and SQLite) and services between plugins, and sc-offline rebuilt on it (CMake first, then its features as built-in plugins). Nothing built yet.
- **Crash containment for plugin callbacks** (`sco::SetCalloutGuard`, `sco::plugins::ContainCallouts`): every task, event callback, command and `invoke` `done` callback a plugin owns now runs through the loader's crash guard, so a native plugin that faults in `tick` or a command is disabled instead of ending the game, and a faulting command answers `SCO_CRASHED`. Before, only `query`, `load` and `unload` were guarded. `done` is no longer called for an owner released during its own command. The loader never unmaps a plugin whose `Release` failed, keeps a nested crash's state, loads DLLs by absolute path (`LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR` needs one), rebuilds the content index without dropping loaded packs, and refuses a pack it can't read completely.
- **sco-lua limits**: error objects are never converted outside protected mode (a number error at the memory cap could `abort()` the game); at most 64 functions per event and 16 queued tasks per script; `table.unpack`/`pack`, `string.byte`/`char`, long plain `find` needles and long bracket classes are charged in proportion to their work. `sco-plugin-check` applies the host's exact `plugin.ini` and command rules.
